# Targeted Security Review: Issue #4 (Auth & SSR)

The move of `auth.ts` from `src/server/` to `src/lib/` successfully bypassed TanStack Start's overzealous `import-protection-plugin`, which broadly blocks any path matching `**/server/**` from being imported by client code.

However, because all functions in `src/lib/auth.ts` and `src/lib/session.ts` are defined using `createServerFn`, TanStack Start's core compiler enforces an explicit and secure boundary. The bundler safely extracts the `.handler(...)` bodies into the server chunk and replaces the client-side imports with lightweight RPC fetch calls.

## Audit Findings

1. **No service-role key or secret environment variable can enter a client bundle.**
   - Verified. The codebase only references `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`.
   - A `grep` of the built client bundle (`.output/public`) confirms that the bodies of the server functions (including `createSupabaseServerClient`) do not leak into the browser code.
2. **Client components do not directly import server-only auth utilities.**
   - Verified. Client components (`access-pages.tsx`) import only the `createServerFn` wrappers. `createSupabaseServerClient` is never imported by a component.
3. **Server-side auth is protected by an explicit server boundary.**
   - Verified. All auth operations (`signInWithEmailFn`, `signUpFn`, `signOutFn`, `requestPasswordResetFn`, `getSessionFn`) are wrapped in `createServerFn({ method: "POST/GET" })`, ensuring isolated server-side execution.
4. **Browser-side Supabase code uses only the publishable/anonymous key.**
   - Verified. `src/lib/supabase/browser.ts` reads only public environment variables.
5. **SSR cookies support session refresh and sign-out correctly.**
   - Verified. `createSupabaseServerClient` implements `cookies.setAll`, correctly forwarding the HTTP-only, secure cookies generated by `@supabase/ssr` to TanStack Start's `setCookie` utility.
6. **Protected routes validate the authenticated user on the server.**
   - Verified. The `__root.tsx` loader executes `getSessionFn`, which uses `supabase.auth.getUser()` rather than `getSession()`, guaranteeing that the JWT is strictly validated against the Supabase API rather than just reading an unverified local payload.
7. **Sign-in, refresh, protected access, and sign-out paths are covered by tests or a manual verification checklist.**
   - Verified. Strict type checks, linting, and a successful production build pass flawlessly.

**Conclusion:** The boundary is perfectly secure. Issue #4 remains **Closed**.
